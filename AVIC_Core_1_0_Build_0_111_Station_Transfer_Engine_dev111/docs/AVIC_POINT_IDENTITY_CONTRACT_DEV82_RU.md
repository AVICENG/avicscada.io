# AVIC Core — контракт идентификации точек и адресации (DEV82)

## Статус и область применения

Этот документ задаёт единый контракт представления точек в AVIC. Он не объявляет AVIC полностью сертифицированным по BACnet, Modbus или IEC 61131-3. Протоколы сохраняют собственные адресные пространства; AVIC нормализует их для дерева, поиска, привязок, аудита и лицензирования.

## 1. Три разных идентификатора

Каждая точка AVIC имеет раздельно:

1. **AVIC UID** — неизменяемый внутренний UUID/ID. Не зависит от имени, адреса или положения в дереве.
2. **Native identity** — родная идентичность точки в источнике.
3. **Display name / symbolic address** — читаемое представление для инженера. Может быть изменено без смены UID.

Имя не является ключом. Нельзя строить связи только по отображаемому имени.

## 2. BACnet

Родная идентичность BACnet-объекта — пара `Object_Type + Object_Identifier instance`, в контексте BACnet Device. Пример: `analog-input,4`. Устройство имеет собственный Device Instance.

- Уникальность Object_Identifier проверяется в пределах устройства.
- Object_Name должен быть уникальным в пределах устройства.
- В AVIC хранить отдельно Device Instance, Object Type, Object Instance, Object_Name и адрес устройства/сети.
- Сокращения `AI-4`, `AO-5`, `BI-2`, `BO-3` допустимы только как display label, не как замена BACnet Object Identifier.
- Нельзя угадывать тип объекта или instance по имени точки.

Основание: ANSI/ASHRAE 135; официальный текст Addendum cu к Standard 135-2024 подтверждает уникальность Object_Identifier и Object_Name в пределах BACnet Device.

## 3. Modbus TCP/RTU

Modbus не задаёт единого универсального символьного номера вида `40001` в поле адреса PDU. В запросе PDU адреса регистров/битов начинаются с нуля.

AVIC обязан хранить:
- таблицу: Coils / Discrete Inputs / Input Registers / Holding Registers;
- PDU offset (0…65535);
- function code, допустимый для этой таблицы;
- Unit Identifier / идентичность устройства;
- формат данных и порядок байтов/слов, если значение многорегистровое;
- отдельное vendor/reference label, если документация оборудования использует 00001/10001/30001/40001 или иной формат.

Пример: conventional reference `40001` для Holding Register обычно соответствует PDU offset `0`. В UI показывать оба значения, если применимо. Нельзя автоматически прибавлять/вычитать единицу без явного address-basis драйвера.

Основание: Modbus Organization, Modbus Application Protocol Specification V1.1b3, раздел 6.3: PDU register addressing starts at zero.

## 4. FBD / IEC 61131-3

IEC 61131-3 определяет FBD как графическую сеть экземпляров функциональных блоков, функций, переменных, литералов и меток; интерфейс FB включает входные, выходные и внутренние переменные.

AVIC использует:
- UID документа, страницы, экземпляра блока и порта;
- объявленное имя порта функционального блока (например, `PV`, `SP`, `ENABLE`, `OUT`, `P`, `I`, `D`);
- порядковый индекс порта как дополнительную техническую координату, не вместо имени;
- короткий код страницы `P1`, `P2` и далее;
- номер экземпляра блока как отображаемую метку.

Пример symbolic address: `P1.PID_LOOP_4.PV`. Это соглашение отображения AVIC в IEC-style форме, а не утверждение, что IEC предписывает именно такой формат адреса.

FBD point native identity строится из неизменяемых идентификаторов: `fbd://<document-uid>/<page-uid>/<module-uid>/<port-uid>`. Переименование страницы/блока/порта не меняет native identity; индекс порта хранится дополнительно для адресации массива и обратной совместимости.

## 5. Типизация и классификация

Общая модель хранит раздельно:
- direction: input / output;
- data type: BOOL, SINT, INT, DINT, USINT, UINT, UDINT, REAL, LREAL, STRING и другие поддерживаемые типы;
- engineering unit;
- range/scaling;
- quality;
- source/provenance;
- access/command capability;
- licensing state.

Дерево группирует точки по четырём направлениям/типам: Analog Inputs, Discrete Inputs, Analog Outputs, Discrete Outputs. Если конкретный источник не предоставляет соответствующий класс, AVIC не создаёт фиктивные точки; пустая категория остаётся пустой.

## 6. Уникальность и происхождение

- UID глобально неизменяем.
- Native identity уникальна в своём пространстве источника.
- Для FBD в одном документе запрещено публиковать один и тот же source output port более одного раза.
- FBD point source должен ссылаться на существующие page, module и output port.
- Display names могут повторяться в разных пространствах имён; при необходимости уникальности используется область (device/document/project), а не глобальное ограничение имени.
- Удаление соседней точки/порта не перенумеровывает существующие UID и не меняет их source references.
- Изменение отображаемого имени не меняет связи и происхождение.

## 7. Лицензирование

Созданная FBD point несёт метаданные `pending_core_registration`. Это означает ожидание регистрации в лицензирующем ядре, а не выданную лицензию. Учёт должен происходить один раз по стабильному counting key при фактическом использовании точки в лицензируемой функции. Само обнаружение или создание не должно автоматически списывать лимит.

**Ограничение DEV82:** интеграция этого статуса с полноценным серверным License Manager и подтверждение регистрации Core остаются отдельным этапом. UI не должен выдавать pending за licensed.

## 8. Границы реализации DEV82

- FBD Studio остаётся authoring-only; граф не компилируется в исполняемый runtime.
- FBD point в текущей форме публикуется из выходного порта блока. Категории Input оставлены в общей модели на будущее и не создают фиктивных входных точек.
- Для BACnet/Modbus этот контракт задаёт целевую модель хранения; конкретная корректность каждого драйвера должна подтверждаться отдельными протокольными тестами и реальным оборудованием.
