# AVIC — первичный аудит каталога Niagara (DEV112)

Дата: 2026-11-25  
Статус: первичная инвентаризация; технический и лицензионный аудит не завершён.

## 1. Где находится каталог

Каталог `niagara/` обнаружен в корне ветки `main`. На момент проверки в нём 712 файлов/записей дерева, включая библиотечные JAR-модули и документацию. В ветке `dev112-station-transfer-reliability` каталога `niagara/` нет: DEV112 была создана до появления этой папки. Каталог не копировался в DEV112.

## 2. Важное ограничение по лицензии

В `niagara/lib/licenseAgreement.txt` содержится EULA Tridium от 28 июля 2015 года. В прочитанном тексте указаны ограничения на модификацию, декомпиляцию/дизассемблирование, создание производных работ и распространение Licensed Software; отдельно ограничено включение кода и документации Niagara в сторонний продукт. В `readmeLicenses.txt` перечислены сторонние компоненты и условия их лицензирования.

Поэтому:
- не включать JAR, DLL, классы, исходники или фрагменты Niagara в AVIC;
- не декомпилировать и не извлекать реализацию из бинарных модулей;
- не копировать Niagara-документацию в руководство AVIC;
- не считать наличие файла в GitHub разрешением на его использование или распространение;
- перед любым использованием материалов проверить правообладание и условия лицензии с юристом/лицензиаром.

**Риск репозитория:** если репозиторий остаётся публичным, лицензированные бинарные файлы Niagara доступны публично. Рекомендация — немедленно сделать репозиторий Private и отдельно согласовать удаление таких файлов из Git-истории/публичных объектов. Простое удаление последним коммитом не удаляет старые версии из истории. Это действие не выполнялось автоматически.

## 3. Что обнаружено по названиям файлов

В `niagara/modules` присутствуют имена модулей, указывающие на следующие функциональные области:
- BACnet: `bacnet-rt`, `bacnet-ux`, `bacnet-wb`, BACnet utility/alarm/router модули;
- Modbus: `modbusCore`, `modbusTcp`, `modbusAsync`, slave-модули;
- Trend: `TrendN4`, `TrendEasyBindingGraphics`, а также отдельный каталог `LEGACY_TREND_DRIVER`;
- инженерные инструменты: `kitControl`, `wiresheet`, `program`, `driver`, `easyBinding`;
- графика: `kitPx`, `kitPxBuilding`, `kitPxHvac`, `kitPxGraphics`, `pxEditor`, `svg`;
- эксплуатация: `alarm`, `history`, `schedule`, `backup`, `report`, `PointDatabaseManager`;
- дополнительные интеграции: OPC/OPC UA, oBIX, SNMP, MQTT, LonWorks и другие.

Это инвентаризация по именам, а не подтверждение качества, совместимости или возможности повторного использования реализации.

## 4. Отдельно о LEGACY_TREND_DRIVER

Файл `niagara/LEGACY_TREND_DRIVER/readme.txt` прямо говорит, что эти legacy-файлы предназначены только для обновления станции с версии 2.1; их копируют в modules перед Station Upgrade Service и удаляют после завершения и проверки обновления.

Вывод: **не использовать эти файлы как готовый обычный Trend-драйвер AVIC**. Они относятся к процедуре миграции старой станции.

## 5. Что AVIC должен изучить как независимые функциональные требования

Изучать по доступным руководствам и наблюдаемому поведению, не копируя защищённую реализацию:
1. Драйверная модель: discovery → устройство → точки → качество данных → polling/COV → диагностика и reconnect.
2. Инженерная модель объектов: компоненты, типы, свойства, связи, метаданные, единицы измерения и состояния.
3. FBD/Wiresheet: создание блоков, типизированные соединения, проверка циклов/типов, онлайн-значения, симуляция, публикация.
4. Graphics: повторно используемые HVAC-символы, bindings, навигация между страницами, runtime-обновление.
5. Alarm/History/Schedule: жизненный цикл тревог, подтверждение, архивирование, календарные расписания и исключения.
6. Point Database Manager: импорт/экспорт точек, массовое редактирование, шаблоны и контроль дубликатов.
7. Backup/Restore/Commissioning: проверка восстановления, перенос станции, аудит изменений и откат.
8. Диагностика: здоровье драйвера/устройства, качество данных, журнал связи, тайм-ауты и безопасные повторные попытки.

## 6. Приоритеты для AVIC

**Высокий приоритет:** BACnet/IP и Modbus TCP; импорт и управление точками; единая модель качества данных; FBD runtime и редактор; HVAC graphics и bindings; alarm/history/schedule; backup/restore и безопасный commissioning.

**Средний приоритет:** OPC UA, MQTT, SNMP, oBIX — через независимые адаптеры после стабилизации Driver SDK.

**Отложить:** большой набор vendor-specific LonWorks/legacy-драйверов и интеграции, не подтверждённые реальными объектами и тестовыми стендами.

## 7. Следующий этап аудита

- Сопоставить эти сценарии с фактическим кодом AVIC: реализовано / частично / отсутствует / не проверено.
- Для каждого приоритета создать AVIC-native спецификацию, API-контракт и тесты.
- Не переносить бинарные Niagara-модули в сборки, CI artifacts или дистрибутивы AVIC.

## 8. Статус автоматических тестов DEV112

Для ветки `dev112-station-transfer-reliability` добавлен GitHub Actions workflow:
`.github/workflows/avic-core-ci.yml`.

Он запускает:
- Python 3.11, 3.12 и 3.13 на Ubuntu;
- Python 3.13 на Windows;
- установку `.[dev]`, `pip check`, `compileall`, полный `pytest`;
- сохранение JUnit-отчётов как workflow artifacts.

Первый запуск инициирован после добавления workflow. Результат должен быть внесён в этот журнал только после завершения GitHub Actions. Автоматический CI не заменяет проверку на целевых Windows-системах и реальном BACnet/Modbus-оборудовании.
