# AVIC — надёжность Rust Communication Engine

Дата: 28.11.2026

## Назначение

Rust Communication Engine оценивается по двум независимым осям: производительность и отказоустойчивость. Ускорение не компенсирует потерю событий, неверное качество точки, зависший процесс или нарушение изоляции станции.

## Уже реализованные защитные механизмы

- Отдельный процесс Worker на экземпляр драйвера и поколение запуска.
- IPC с версионируемым envelope, проверкой installation/project/station/driver/worker/generation.
- Монотонная последовательность сообщений; дубликаты и устаревшие поколения отклоняются, разрывы учитываются в диагностике.
- Ограничение IPC frame до 1 MiB.
- Ограниченная очередь асинхронных событий (256 записей).
- Переполнение очереди допускает отбрасывание только явно заменяемых telemetry/sample; критическое событие приводит к fencing Worker.
- Таймаут команды завершает Worker; stderr хранится ограниченным хвостом.
- Любая ошибка stdout reader делает IPC-сессию недействительной и сбрасывает состояние `started`; startup повторно проверяет состояние процесса и reader после получения start ACK.
- Worker не получает shell, запускается с ограниченным окружением; секреты запрещены в конфигурации и IPC.
- Modbus TCP-клиент сбрасывает TCP-сессию после timeout/ошибки/некорректного ответа и подключается заново при следующем чтении.

## Исправление DEV270/DEV271

Обнаружен сценарий: дочерний Worker закрывает stdout (IPC EOF), но сам остаётся жив. Ранее Supervisor регистрировал EOF, однако при отсутствии ожидающей команды процесс мог остаться без канала управления.

DEV270 ввёл правило: EOF при ещё работающем процессе — отказ IPC-сессии; Supervisor завершает процесс, при необходимости применяет kill. CI выявил, что `sys.stdout.close()` в тестовом дочернем процессе не гарантировал закрытие pipe descriptor. DEV271 использует прямое закрытие fd 1 (`os.close(1)`). Любая ошибка reader теперь выставляет `reader_failed`, сбрасывает `started`, а startup проверяет, что ACK не пришёл одновременно с уже отказавшей IPC-сессией.

## Матрица обязательной надёжности

1. **Процесс:** неожиданный exit, EOF при живом процессе, зависание, timeout, повторное закрытие, очистка дескрипторов.
2. **IPC:** короткий header/body, oversized frame, malformed JSON, unknown fields, неверная identity/generation, replay и sequence gap.
3. **События:** переполнение telemetry и critical queue, отсутствие тихого drop аварий/обнаружения/состояния.
4. **Сеть:** timeout, reset, late response, malformed protocol response, reconnect, DNS/address change.
5. **Точки:** BAD/UNCERTAIN при потере связи, запрет устаревшему Worker публиковать данные после смены generation.
6. **Нагрузка:** 1k устройств / 100k точек, p50/p95/p99, память, CPU, очереди, многократные disconnect/reconnect.
7. **Soak:** 24 часа как первый gate, затем 72 часа на длительной стабильности; проверка утечек и дрейфа памяти.
8. **Платформы:** Windows и Linux; одинаковые fault-injection сценарии и диагностические поля.

## Текущие ограничения

- Текущий benchmark — синтетический Modbus TCP loopback, не физические контроллеры и не доказательство производственной ёмкости.
- 24/72-часовой soak ещё не закрыт.
- Текущие unit tests не заменяют packet-loss/network-chaos и аппаратные испытания.
- Автоматический restart не должен происходить внутри старого Worker object: новый запуск должен получать новое generation и проходить полную инициализацию через Driver Manager/Supervisor.
- Нельзя маркировать Rust или драйвер как промышленно готовый только по успешной сборке или benchmark.

## Gate для жёлто-зелёного статуса

Программный gate считается закрытым после прохождения Windows/Linux тестов, fault-injection, reconnect/soak, контроля качества точек и документирования ограничений. Реальное оборудование — отдельный gate; его нельзя подменять симулятором.
