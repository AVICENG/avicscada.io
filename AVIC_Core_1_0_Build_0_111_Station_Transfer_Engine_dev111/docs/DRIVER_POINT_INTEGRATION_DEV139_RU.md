# Единый контракт точек драйверов AVIC — DEV139

Дата: 25.11.2026
Ветка: `dev113-network-drivers`

## Цель

Любой полевой или интеграционный протокол должен создавать и обновлять обычные сущности `Point` станции. FBD, Graphics, Web Pages, alarms и history не должны зависеть от BACnet/Modbus/MQTT-классов или знать формат адреса протокола.

## Уже подтверждено по текущему коду

1. `PointRuntimeService.publish(point_id, value, quality, timestamp, source_driver_id)` — общий вход публикации для физических точек.
2. `PointRuntimeService.read(point_id)` — единый путь чтения актуального значения, качества, времени, единиц, типа и источника.
3. BACnet/IP adapter и Modbus TCP adapter публикуют через этот контракт. MQTT adapter также использует тот же контракт, но production runtime/factory не подключён и каталог должен оставаться PLANNED.
4. FBD `POINT_INPUT` получает точку по AVIC `point_id` через `core.point_runtime.read`; качество, отличное от GOOD, должно блокировать использование значения.
5. Graphics `PointBinding` хранит `point_id`, а Graphics Service разрешает имя физической точки из общего реестра.
6. Страница Web Pages включает графические документы станции; привязка точки на странице должна оставаться привязкой к Graphic PointBinding, а не к типу драйвера.

## Обязательный сквозной поток

`Protocol Adapter -> PointRuntime.publish -> Point repository/Runtime -> FBD POINT_INPUT`

`                                                       -> Graphics PointBinding -> Web Page`

`                                                       -> Alarm/History consumers`

Каждая точка должна иметь один постоянный AVIC UUID. Native identity протокола (например BACnet Device/Object, Modbus unit/function/address, MQTT topic, OPC UA NodeId) хранится как внешний адрес/идентификатор и не заменяет AVIC UUID.

## Правила для всех будущих адаптеров

- Публиковать только в физические INPUT точки, принадлежащие своему DriverInstance; OUTPUT запрещён.
- Проверять тип данных и диапазон до записи в Point Runtime.
- Передавать timestamp с часовым поясом; если устройство не предоставляет достоверное время, фиксировать время приёма и отдельно указывать источник времени.
- При потере связи менять качество на BAD_COMMUNICATION, сохраняя последнее значение и timestamp последнего успешного измерения.
- Не подменять плохое качество GOOD; FBD и команды не должны использовать BAD/UNCERTAIN/STALE данные как валидный сигнал.
- Не хранить пароли, токены, ключи и сертификаты в config экземпляра; использовать SecretStore.
- Никаких сетевых операций при создании/импорте конфигурации; только явный запуск.
- Драйверный адаптер не должен писать в полевые устройства, пока отдельная безопасная write-модель не прошла проектирование, RBAC, lease, audit, simulation и acceptance.
- Драйвер не должен создавать отдельную модель runtime-точек для своего протокола.

## Обязательные сквозные тесты перед объявлением протокола готовым

Для каждого протокола:
1. Создать Station, Device и Point с постоянным AVIC UUID и привязкой к DriverInstance.
2. Подать валидное измерение через адаптер и проверить `PointRuntime.read`.
3. Прочитать эту же точку через FBD `POINT_INPUT` и проверить совпадение значения, качества и timestamp.
4. Привязать ту же точку к GraphicElement через `PointBinding`; проверить, что Graphics Service и Web Page возвращают тот же point_id.
5. Проверить неверный тип, неверного владельца драйвера, OUTPUT-точку, повторную публикацию, BAD_COMMUNICATION и восстановление после нового GOOD sample.
6. Проверить, что после остановки/удаления DriverInstance ссылки FBD/Graphics не теряются и точка не получает фиктивные значения.
7. Проверить изоляцию по station_id: чужая станция не может читать/публиковать/привязывать точку без явного межстанционного механизма.

## Что ещё не закрыто

- В текущем PR нет единого мастера импорта точек для всех протоколов. Сейчас протокольные конфигурации и создание физических Point должны быть связаны в один транзакционный onboarding workflow.
- Нужен общий Point Binding/Discovery Import Service: предпросмотр найденных точек, выбор, сопоставление native identity -> AVIC Point, проверка типов/единиц/направления, дедупликация, пакетный импорт и rollback.
- Нужен общий сквозной тестовый набор, запускаемый для каждого адаптера через один параметризованный adapter contract.
- Нужны тесты чтения точки в FBD и её отображения на Web Page после обновления каждого адаптера, а не только изолированные тесты драйвера.
- Нельзя считать MQTT готовым, пока нет factory, SecretStore/TLS wiring, reconnect/last-will policy и broker acceptance.
- OPC UA, SNMP, KNXnet/IP, LonWorks, oBIX, Haystack и Trend IP остаются отдельными задачами; каталог не должен показывать их как работающие без реального адаптера.
- Trend IP/vCNC нельзя реализовывать догадками: требуется подтверждённая спецификация framing/handshake или законно полученный trace/SDK и interoperability tests.

## Границы и безопасность

Исключённые проектом Niagara Fox, CCN, Andover и N2 не включать. Niagara JAR не декомпилировать и не переносить код/ресурсы. Семейства модулей используются только как ориентир; независимые реализации строятся по открытым спецификациям и собственным тестам.

## Definition of Done для интеграции

Интеграция считается завершённой только если:
- точка, созданная из любого поддерживаемого протокола, отображается в Point Manager;
- та же точка выбирается в FBD POINT_INPUT без специальных протокольных блоков;
- та же точка выбирается в Graphics PointBinding и отображается на опубликованной Web Page;
- runtime value, quality, timestamp и unit совпадают во всех потребителях;
- все сквозные тесты проходят на Windows и Linux;
- документация содержит пошаговый сценарий discovery -> import -> bind -> simulate -> publish;
- драйвер имеет отдельный подтверждённый статус: planned / partial read-only / hardware-tested read-only / write-capable (последнее требует отдельного допуска).

Этот документ фиксирует целевую интеграционную архитектуру и проверяемые критерии. Он сам по себе не объявляет новые протоколы реализованными.
