# Лицензионная проверка Core и Driver Manager

## Что реализовано в этом изменении

- `CoreApplication` принимает пару `license_service` + `license_file` и передаёт её в `CoreObjectService`. Проверка лимита уникальных объектов `Point` выполняется внутри транзакции сохранения графа; обновление существующего UUID не расходует дополнительный слот.
- `InstallationLicenseService.assert_feature_enabled()` проверяет действительность подписи/срока/Host ID (через `inspect`) и точное совпадение ключа функции с подписанным списком `features`.
- `DriverManagerService.catalog()` публикует `license_feature` для каждого драйвера.
- Создание экземпляра, изменение конфигурации остановленного драйвера и запуск требуют соответствующего entitlement, если лицензионный сервис подключён. Остановка и диагностика остаются доступными для безопасного вывода из эксплуатации.
- Уже работающая сессия при повторном вызове `start_instance()` возвращает текущую диагностику до повторной проверки entitlement: изменение статуса лицензии не останавливает уже работающий процесс автоматически.

## Ключи функций

Ключи сравниваются точно, без неявного преобразования. Например: `driver.bacnet-ip`, `driver.modbus-tcp`, `driver.knxnet-ip`. Подписанный файл лицензии должен содержать именно эти строки в `features`.

## Подключение

Создайте `LicenseManager` с публичным Ed25519-ключом AVIC, затем `InstallationLicenseService(data_dir, manager)`. Передайте оба объекта в композиционный корень:

```python
core = CoreApplication(
    data_dir,
    license_service=installation_license_service,
    license_file=path_to_signed_license,
)
```

Передача только одного из двух параметров является ошибкой конфигурации.

Для Workbench доступны переменные окружения `AVIC_LICENSE_PUBLIC_KEY` (путь к публичному PEM Ed25519 ключу AVIC) и `AVIC_LICENSE_FILE` (путь к подписанному `.aviclic`). Нужно задать обе переменные. Если задана только одна, запуск Workbench завершается с явной ошибкой, а не молча отключает лицензионную проверку. Для обязательного лицензионного режима в коммерческой поставке задайте `AVIC_LICENSE_REQUIRED=1`: тогда запуск без двух остальных параметров будет запрещён. В режиме разработки флаг можно не задавать. Приватный ключ выпуска лицензий в установку не включается.

## Ограничение текущего этапа

Если `license_service` не передан, Core остаётся в режиме разработки/совместимости и лицензионные entitlement-проверки драйверов не выполняются. Это не следует считать готовым коммерческим режимом. Подключение конфигурации публичного ключа и файла лицензии к установщику/Workbench, отзыв/перевыпуск лицензий, перенос Host ID, UI статуса/остатка точек и сквозная авторизация всех API остаются отдельными задачами. Закрытый ключ выпуска лицензий не должен попадать в клиентскую поставку.

## Проверки

Добавлены тесты на передачу сервиса через `CoreApplication`, лимит точек в штатном пути, точные ключи возможностей драйверов и отказ создания/запуска при отсутствии entitlement. Результаты выполнения тестов фиксируются после CI для этого коммита.

## API статуса лицензии для Workbench

- `GET /api/licensing/status` возвращает configured/valid/reason, имя заказчика, ID лицензии, Host ID, лимит, число активных лицензируемых точек, остаток и список feature keys.
- `GET /api/licensing/point-usage` возвращает счётчики типов точек и теперь учитывает лимит из подписанной лицензии, если лицензия подключена.
- API не возвращает путь к файлу лицензии, PEM-ключ или приватные данные подписи.
- В незапущенном коммерческом режиме API явно возвращает `configured=false`, `valid=null`, `LICENSE_NOT_CONFIGURED`, а не изображает наличие лицензии.


Коммерческий инсталлятор должен устанавливать `AVIC_LICENSE_REQUIRED=1` по умолчанию и передавать публичный ключ и лицензию как защищённую конфигурацию установки. Это обязательная интеграция поставки; отсутствие этой настройки нельзя считать коммерчески безопасным режимом.


## Учёт лицензируемых точек — правила активации

В каталоге Core каждая точка хранит `point_type`, `licensed_active` и `published`.
Обнаруженная/импортированная точка может быть сохранена как черновик с
`licensed_active=false`: она видна инженеру и не расходует лимит. Для физических
точек без явного признака активности сохраняется обратная совместимость: старые
записи считаются активными. Расчётная точка учитывается только при одновременных
`published=true` и `licensed_active=true`. Программные и ручные точки учитываются
при явном `licensed_active=true`.

Проверка выполняется внутри транзакции репозитория по разнице между множествами
активных ID до и после изменения графа. Поэтому она охватывает как создание новой
активной точки, так и перевод существующего черновика в активное состояние;
обновление уже активной точки не занимает второй слот. Удаление/деактивация
освобождает слот. Счётчик API и транзакционная проверка используют одну функцию
`summarize_point_usage`.

Важно: интеграции Discovery/Import, FBD Publish, Graphics Bindings, Alarm,
History, Scheduler и Control должны явно выставлять `licensed_active` в момент
подключения точки к соответствующей рабочей функции. Само обнаружение устройства
или наличие FBD-провода не активирует точку автоматически.


## Привязка точки к инженерной функции

Импорт Discovery сохраняет физические точки как неактивные. При сохранении FBD-стратегии
с блоками `POINT_INPUT` Core регистрирует использование с ключом конкретного документа
(`logic:<document_id>); при сохранении мнемосхемы — `graphics:<document_id>`.
Состояние и проверка лимита обновляются в той же транзакции, что и соответствующий
инженерный документ. Одна точка, одновременно используемая в нескольких местах,
учитывается один раз. Удаление последней привязки одного документа не деактивирует
точку, пока остаётся другая зарегистрированная функция.

На текущем этапе автоматическая регистрация включена для FBD, Graphics, Scheduler и History.
Scheduler регистрирует полный набор точек расписания под ключом
`schedule:<schedule_id>` при привязке и обновляет его при отвязке. Проверка лимита
выполняется до фиксации новой привязки; при отказе лицензии запись расписания не
создаётся. Одна точка, используемая одновременно в FBD, Graphics и Scheduler,
по-прежнему занимает один слот.

Scheduler и Core Object Repository используют разные SQLite-базы. Поэтому bind
использует компенсирующее восстановление прежнего usage-набора при ошибке записи;
unbind фиксирует удаление привязки, затем обновляет usage. При сбое между этими
операциями возможна временная лишняя активная ссылка, но не преждевременное
освобождение занятого слота. Нужна отдельная reconcile-процедура.

History хранит явные конфигурационные привязки в `history_bindings`; API включает и
отключает архивирование точки, проверяет принадлежность станции и регистрирует полный
набор точек станции под ключом `history:<station_id>`. Запись отдельного sample не
создаёт новую лицензионную ссылку.

Для Alarm usage привязан к постоянным доменным объектам `Alarm` (правила/конфигурация),
а не к transient срабатываниям `AlarmService`. Если `Alarm.source_object_id` ссылается
на `Point`, Core регистрирует `alarm:<alarm_id>` в той же транзакции `save_graph`;
изменение источника или удаление правила снимает только его usage-ссылку. Если источник
— Device/Component, дополнительный Point-слот не активируется. Это намеренно не считает
каждое новое событие отдельной точкой. Для Control требуется подключить usage к
постоянной конфигурации команд/управления.


## Защита от удаления используемой точки

CoreObjectService запрещает удалять `Point`, пока в `licensed_usage` остаются активные
ссылки инженерных функций. Сначала требуется удалить/отвязать FBD, Graphics, Alarm,
History, Scheduler или Control usage соответствующим сервисом; только после этого
точка может быть удалена. При пакетном удалении правила Alarm их usage очищается в той
же транзакции перед проверкой Point. Это предотвращает потерю точки, на которую ещё
ссылается действующая инженерная конфигурация.


## Сохранение базовой активности точки

При первом добавлении инженерной usage-ссылки Core сохраняет исходное состояние точки в `licensed_base_active`. Пока есть хотя бы одна ссылка, `licensed_active=true`. После удаления последней ссылки восстанавливается исходная активность, а не безусловно выставляется `false`. Это важно для обратной совместимости старых физических точек, которые считались активными до введения usage-учёта. Версии объектов, изменённых при автоматической регистрации usage внутри `save_graph`, возвращаются уже после всех изменений в транзакции.
