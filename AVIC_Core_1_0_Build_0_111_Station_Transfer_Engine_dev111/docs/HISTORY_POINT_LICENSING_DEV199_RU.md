# Настройка архивирования точек и лицензирование — DEV199

## Назначение
Архивная точка — это инженерная точка, явно включённая в конфигурацию History. Сам факт получения или ручной записи sample не должен активировать лицензионный слот: слот относится к настроенной функции архивирования.

## API
- `GET /api/stations/{station_id}/history/points` — список точек, включённых в архивирование станции.
- `PUT /api/stations/{station_id}/history/points/{point_id}` с телом `{"enabled": true}` — включить точку.
- Тот же PUT с `{"enabled": false}` — отключить точку.
- Операции требуют локального инженерного доступа и попадают в Audit.

## Правила
- Включать можно только объект `Point`, связанный с устройством указанной станции.
- Межстанционная привязка запрещена.
- Перед сохранением новой конфигурации History общий лицензионный сервис получает полный набор точек станции с ключом `history:<station_id>`.
- Одна и та же точка, одновременно используемая FBD, Graphics, Scheduler и History, занимает один слот.
- Отключение History снимает только ссылку History; точка остаётся лицензируемой, если её использует другая функция.
- Sample append не регистрирует новый usage и не создаёт повторный расход лицензии.

## Хранение и отказоустойчивость
Конфигурация сохраняется в `history_bindings` внутри БД History. Репозиторий инженерных объектов и БД History раздельны, поэтому это не единая ACID-транзакция. Включение сначала проверяет/активирует usage, затем сохраняет binding; при ошибке сохранения выполняется компенсация. Отключение сначала удаляет binding, затем обновляет usage. Если второй шаг завершится ошибкой, возможна временная лишняя активная ссылка, но не преждевременное освобождение слота. Для промышленной эксплуатации требуется reconcile-процедура.

## Ограничения
- Этот этап добавляет service API и HTTP API, но ещё не полноценный визуальный редактор конфигурации архивов и расписаний опроса.
- `HistoryService.append` пока не запрещает запись sample для не настроенной точки: это оставлено для обратной совместимости и ручного импорта. Автоматический сбор должен опираться на configured bindings.
- Политики deadband, интервалы, COV, буферизация, ротация, retention и high-load acceptance остаются отдельными задачами.
