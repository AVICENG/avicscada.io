# AVIC FBD — Niagara / Trend SET parity specification (DEV176)

Дата: 2026-11-26  
Ветка: `dev113-network-drivers`  
Базовый HEAD аудита: `fa76a6aff5925c6d4a5a245b346904035978fb15`  
Статус: архитектурная спецификация и аудит текущего поведения; это не заявление о завершённой реализации.

## 1. Цель и границы

Документ фиксирует независимые требования к инженерной модели FBD AVIC по материалам Niagara Workbench / Wiresheet и Trend System Engineering Tool (SET). Заимствуются функциональные принципы, а не исходный код, бинарные модули, закрытые форматы или защищённые графические ресурсы.

Цель — единая многостраничная стратегия, в которой:
- страницы являются представлениями одного проекта/стратегии;
- блоки и порты имеют стабильные UID и типизированные контракты;
- локальные и межстраничные связи являются сохраняемыми объектами модели;
- Connective переносит сигнал между страницами, а To Connective показывает соответствующую точку на стороне источника;
- Go To выполняет только навигацию и никогда не меняет граф исполнения;
- копирование, удаление, импорт и экспорт не оставляют висячих ссылок;
- компиляция в Core FBD сохраняет семантику и отклоняет непроверенные конструкции;
- исполнение не обходит Point Quality, Command Manager, RBAC, staged publish и аудит.

## 2. Термины — не смешивать

| Объект | Семантика | Влияет на вычисление |
|---|---|---|
| FBD Link / Wire | Связь output-порта с input-портом | Да |
| Connective | Межстраничный alias/proxy конкретного output-порта на странице-получателе | Да, передаёт то же значение |
| To Connective | Навигационный маркер соответствующего Connective на странице-источнике | Нет |
| Go To | Команда перехода к странице/блоку/точке | Нет |
| Page Reference | Стабильная запись связи между исходным портом и proxy-портом | Да, как адресация Connective |
| FBD Point | Публикуемая точка, экспортированная из выхода блока | Да, как источник/потребитель через Point Runtime, но не является Connective |

Connective и To Connective — не два конца обычного пользовательского провода. Источник истины для межстраничной связи — Page Reference с UID и endpoint-идентификаторами. Символы на листах являются представлениями этой записи.

Go To нельзя компилировать в LogicLink и нельзя трактовать как сигнал.

## 4. Целевая модель данных

В Core следует ввести серверную сущность/таблицу межстраничных ссылок. Не использовать имена страниц, имена блоков или номера как первичные ключи.

Рекомендуемый контракт:

```json
{
  "id": "stable-reference-uid",
  "strategy_id": "fbd-studio-document-id",
  "kind": "signal",
  "source": {
    "page_id": "page-uid",
    "module_id": "module-uid",
    "port_id": "output-port-uid",
    "port_index": 0
  },
  "target": {
    "page_id": "target-page-uid",
    "proxy_module_id": "connective-proxy-uid",
    "port_id": "proxy-output-port-uid"
  },
  "signal_type": "bool",
  "label": "Fan enable",
  "revision": 1,
  "enabled": true
}
```

Правила:
1. UID reference неизменяем; переименование страницы/блока не меняет ссылку.
2. Source должен указывать на существующий output-порт реального блока, не на To Connective.
3. Target должен указывать на CONNECTIVE proxy с одним совместимым выходом.
4. CONNECTIVE proxy не имеет вычислительного алгоритма и не создаёт независимое значение.
5. TO_CONNECTIVE marker обязан ссылаться на ту же reference; отсутствие маркера можно восстановить без изменения сигнальной связи.
6. Удаление/изменение порта, блока или страницы запускает проверку зависимостей и не оставляет молча висячую ссылку.
7. Сигнальный тип берётся из контракта исходного порта; тип proxy и его потребителей сверяется с ним.
8. Качество, timestamp, source/provenance и диагностическое состояние проходят вместе со значением. BAD/UNCERTAIN/STALE/COMM_LOST не превращаются в GOOD.
9. На первом этапе межстанционные ссылки запрещены. Ссылка принадлежит одному FBD-проекту одной станции.
10. Циклы через Connective должны быть обнаружены в общем графе стратегии. Не использовать повторное вычисление UI для маскировки цикла.

## 5. Семантика выполнения и компиляции

### 5.1 Редактор

При соединении входа с CONNECTIVE output редактор создаёт обычный локальный FBD Link от proxy output к target input. Сам межстраничный переход хранится в Page Reference.

### 5.2 Compiler

Compiler должен:
1. проверить весь проект целиком до создания Core-документа;
2. разрешить каждую reference по UID;
3. проверить source page/module/port и target page/proxy/port;
4. проверить парность proxy и To Connective marker;
5. проверить совместимость типов и cardinality входов;
6. построить единый граф стратегии;
7. заменить каждую ссылку на proxy output прямым Core edge от исходного output к потребителю либо на эквивалентный внутренний alias с теми же семантикой и качеством;
8. удалить из исполняемого графа чисто навигационные To Connective markers;
9. проверить циклы и порядок исполнения после раскрытия aliases;
10. вернуть диагностический отчёт с page/module/port UID и человекочитаемыми именами.

Компилятор не должен создавать фиктивный вычислительный узел для To Connective. Для Connective proxy допустим либо явный alias mapping в compiler, либо отдельный нулевой по вычислению alias node в Core, если его semantics и quality propagation тестируются. Предпочтительный первый вариант — раскрытие alias в Core links.

### 5.3 Runtime

- Значение и качество исходного порта должны наблюдаться на всех страницах-получателях без потери качества.
- Fan-out одного source output на несколько страниц разрешён.
- Повторные references на одну и ту же пару source/target запрещены.
- Для одного входа допускается только одна активная связь, если конкретный тип входа явно не объявляет multi-input.
- Обновление источника распространяется на все потребители в рамках одного согласованного FBD tick.
- Нельзя допускать зависимость исполнения от открытой в Workbench страницы.
- Закрытие Workbench не останавливает станцию/Core Runtime.

## 6. Дублирование, удаление, импорт и экспорт

### 6.1 Дублирование отдельной страницы

Текущая реализация копирует блоки и локальные links, но не переносит references. Это необходимо исправить.

До реализации пользовательского сценария определить внешние зависимости:
- references, у которых source и target находятся на копируемой странице (обычно невозможный случай при cross-page reference, но валидатор обязан определить его);
- inbound references: source остаётся на другой странице, target proxy расположен на копируемой странице;
- outbound references: source расположен на копируемой странице, target proxy — на другой странице.

Операция не должна молча переназначать исходные ссылки. Рекомендуемое безопасное поведение:
- по умолчанию дублирование страницы копирует локальные блоки и локальные links;
- при наличии внешних Connective показывается предварительный просмотр зависимостей и предлагаются явные действия: оставить связь с исходным проектным endpoint (если это осознанно), создать отдельную новую reference, либо копировать страницу без внешней связи;
- cancel оставляет проект неизменным;
- все новые UID и tag выдаются заново; исходные UID не меняются.

### 6.2 Копирование всей стратегии / шаблона

Копирование всего FBD-проекта должно создавать новые UID страниц, блоков, портов, links, references, proxy и markers. Все внутренние ссылки должны быть переназначены через полную таблицу old_uid → new_uid. Никакая ссылка копии не должна вести назад в исходную стратегию, если пользователь явно не выбрал внешний shared dependency.

### 6.3 Удаление

- Удаление proxy: запросить удаление соответствующей reference; To Connective marker становится orphan и удаляется/восстанавливается по подтверждённому решению.
- Удаление To Connective marker: удалить только marker или предложить восстановление; сигнальная reference остаётся активной.
- Удаление source block/output: блокировать удаление до явного подтверждения удаления всех outbound references либо предложить заменить источник.
- Удаление страницы: показать inbound/outbound references, затем атомарно удалить/переназначить их по выбранному решению.
- Любая операция — транзакционная, с undo/redo и аудитом.

### 6.4 Import/export и revision

Пакет должен включать schema version, project UID, pages, modules, ports, local links, references, fbdPoints, библиотечные версии и метаданные. Импорт — двухфазный: validate/preview, затем commit. Ошибка не должна оставлять частично импортированный проект.

## 7. Go To и инженерная навигация

Go To — команда Workbench, не часть FBD runtime.

Обязательные переходы:
- Connective proxy → исходный модуль и конкретный выходной порт;
- To Connective marker → proxy на странице назначения;
- FBD Point → исходный модуль/порт;
- ошибка compiler → конкретная страница, блок и порт;
- ссылка в дереве/поиске → соответствующий объект.

Навигация должна:
- активировать нужную страницу;
- выделять объект и порт;
- центрировать объект на рабочем поле;
- показывать breadcrumb/контекст страницы;
- добавлять запись в историю переходов;
- не менять проект и не создавать связи.

Поиск совпадений по имени/типу/номеру не может заменять навигацию по UID: одинаковые имена допустимы, а номера меняются при копировании.

## 8. Требования к проверке

### 8.1 Unit / service

1. Reference создаётся только при существующих source/target page, module, port.
2. Невалидные UID, неверный тип, отрицательный/выходящий за диапазон port index отклоняются.
3. Proxy и marker указывают на один reference UID.
4. Переименование page/module не ломает reference.
5. Удаление/изменение порта выявляет все зависимые references.
6. Fan-out одного выхода на N страниц.
7. Дублирующая reference запрещена.
8. BAD/COMM_LOST/STALE quality сохраняется на proxy и потребителе.
9. Цикл, возникший после раскрытия Connective, отклоняется.
10. Смешивание bool/analog отклоняется на preview.
11. Одна и та же revision compile идемпотентна; stale revision отклоняется.
12. Ошибка компиляции не оставляет частичные Core nodes/links/pages.

### 8.2 UI / browser E2E

1. Создать 3 страницы: Main, Safety, Fan.
2. На Main создать BOOL_INPUT и ANALOG_INPUT.
3. На Safety создать Connective для BOOL_OUTPUT и соединить с логикой Safety.
4. На Fan создать Connective для аналогового выхода и соединить с LIMIT/PID input.
5. Проверить To Connective на исходных страницах и переходы в обе стороны.
6. Переименовать страницы и блоки; проверить сохранение связей.
7. Сохранить, закрыть Workbench, открыть снова; проверить все references.
8. Дублировать страницу с inbound/outbound references и пройти сценарий разрешения зависимостей.
9. Копировать весь проект и убедиться, что UID references переназначены внутри копии.
10. Удалить source block и page через диалог зависимостей.
11. Запустить compile-preview и compile; проверить единый граф и значения.
12. Изменить источник; убедиться, что значения на всех страницах обновляются с тем же quality.
13. Открыть страницу-получатель первой; исполнение не должно зависеть от порядка открытия.
14. Проверить Go To из Connective, To Connective, FBD Point и compiler diagnostic.

### 8.3 Regression / safety

- Не допускать физическую запись из Connective/Graphics/FBD напрямую в driver.
- FBD output остаётся виртуальным/внутренним до отдельного безопасного Command Manager и staged publish.
- Никакие UI-навигационные маркеры не попадают в исполняемый граф.
- Ошибки связей должны блокировать compile/publish, но не повреждать сохранённый исходный проект.
- Workbench exit не останавливает автономную станцию.

## 9. План реализации

### Phase A — Contract and validation
- Ввести строгую серверную схему Page Reference.
- Валидировать все local links и references при сохранении и compile-preview.
- Проверять типы, cardinality, UID, page ownership, proxy/marker pairing и orphan detection.
- Добавить миграцию старых документов без изменения существующих UID.

### Phase B — Compiler and runtime
- Добавить раскрытие Connective alias в единый Core graph.
- Переносить значение, quality, timestamp и provenance.
- Проверить cycles, fan-out и единый tick.
- Исключить To Connective из runtime.

### Phase C — lifecycle and copy
- Реализовать безопасное дублирование страницы с анализом inbound/outbound references.
- Реализовать полное копирование стратегии с remap UID.
- Сделать удаление страницы/блока транзакционным и dependency-aware.
- Добавить preview/commit для import/export.

### Phase D — navigation and UX
- Единый Go To service и история навигации.
- Выделение точного порта, а не только блока.
- Панель Connective/References с source, target, type, quality и статусом.
- Диагностика broken/orphaned references.

### Phase E — acceptance
- Автоматические unit/service tests.
- Playwright browser E2E на Windows и Linux.
- Полный regression набора FBD и station lifecycle.
- Тесты на большой стратегии (тысячи блоков и десятки тысяч связей) с измерением времени preview/compile/tick.
- Протокол испытаний и обновлённая документация пользователя.

## 10. Приёмочные критерии завершения

FBD parity по межстраничным связям не считается завершённым, пока одновременно не выполнено всё:
- все references сохраняются и валидируются сервером;
- compile-preview и compile принимают корректные Connectives и отклоняют некорректные;
- все страницы входят в единый исполняемый граф;
- To Connective остаётся только навигационным маркером;
- копирование/удаление/import/export не создают dangling references;
- Go To работает по стабильным UID;
- quality/provenance распространяются корректно;
- browser E2E и Windows/Linux regression завершены;
- документация и журнал сборки отражают реальные результаты.

## 12. Лицензионная граница

В `docs/NIAGARA_REFERENCE_REVIEW_RU.md` зафиксированы ограничения EULA Tridium и риск распространения лицензированных бинарных материалов. В AVIC разрешено формировать независимые функциональные требования по допустимым руководствам и наблюдаемым сценариям. Не переносить JAR/DLL/код/фрагменты документации/защищённые ресурсы Niagara в AVIC build и не декомпилировать бинарные модули. Trend SET файлы использовать как reference только в рамках прав пользователя и применимых лицензий.
