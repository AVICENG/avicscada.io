# AVIC KNX — переход на XKNX (DEV197)

## Принятое решение

KNX остаётся Python-драйвером AVIC. В качестве протокольного стека используется XKNX, а не собственная реализация KNXnet/IP как основной транспорт.

Зафиксированная зависимость: `xknx>=4.1.1,<5` (MIT, Python >=3.11). Версия 4.1.1 опубликована 5 ноября 2026 года. Диапазон ограничен текущей основной версией, чтобы будущий major upgrade не попадал в сборку автоматически.

## Целевая схема

- Один отдельный KNX Worker process на KNX/IP интерфейс или router.
- Один долгоживущий экземпляр XKNX на соединение.
- Приём телеграмм через telegram callback, без циклического создания туннеля и опроса каждой точки.
- Маппинг групповых адресов и DPT на AVIC Point Runtime.
- Существующие IPC scope, generation fencing, диагностика и единый жизненный цикл AVIC сохраняются.
- Сетевой обмен — через Tunneling или Routing; Secure режимы включаются только при наличии корректной конфигурации и тестов.
- Запись не открывается напрямую из Worker: только через AVIC Command Gateway, RBAC и аудит.

## Правила качества данных

- При потере KNX-соединения связанные точки получают BAD_COMMUNICATION.
- При штатной остановке Worker точки переводятся в STALE.
- Ошибки DPT/конфигурации не должны маскироваться под успешные измерения.
- Пассивный приём групповых телеграмм — основной режим; GroupValueRead используется только по явно заданной политике с ограничением частоты.
- Неизвестные групповые адреса не создают точки автоматически.

## Что уже есть в AVIC до миграции

Существуют Python-модули KNXnet/IP, tunneling, cEMI, декодеры DPT, read-only Point Adapter и тесты транспорта/адаптера. Их поведение и регрессии должны быть сохранены при переходе. Эти модули пока не объявляются заменёнными XKNX.

## Этапы реализации

1. Установить XKNX в dev/test окружениях Windows и Linux; проверить API и жизненный цикл.
2. Создать XKNX-backed transport/session и callback bridge к Point Runtime.
3. Перенести DPT mapping и диагностику, сравнить результаты со старым декодером на golden vectors.
4. Реализовать reconnect/heartbeat, duplicate/stale protection и контролируемый polling.
5. Добавить ETS project import отдельным этапом; не путать CSV import с полным .knxproj.
6. Провести simulator, Windows/Linux CI, hardware acceptance и soak tests.

## Критерий готовности

KNX не повышается до статуса интегрированного драйвера только по факту установки XKNX или успешного импорта Python-модуля. Нужны рабочая постоянная сессия, доставка телеграмм в Point Runtime, корректное качество данных, reconnect, negative tests, Windows/Linux CI и документация эксплуатации.

## Установка

```powershell
python -m pip install -e ".[knx,dev]"
```

Linux использует ту же команду в активированном virtualenv.
